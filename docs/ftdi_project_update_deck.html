Overview

Project Overview & Purpose

What we are building

The project extends the FTDI oscilloscope repository into a professor-facing Qt application that can visualize live waveform data while preserving the existing architectural constraints from the course.

  • Real-time waveform visualization from generated, file-backed, and FTDI-backed sources
  • Two selectable Qt user interfaces over one abstract ioOscilloscopeView boundary
  • Scale and offset handled through ioFilterPipeline, not inside the UI
  • Live acquisition routed through the existing multithreaded FTDI transfer pipeline

Problem we are solving

We needed an oscilloscope design that could satisfy UI, architecture, and FTDI communication requirements at the same time without collapsing everything into one large GUI file.

2 selectable Qt UIs
1 abstract View contract
1 shared circular buffer path
Core message: the UI looks new, but the architectural discipline stayed intact.

Technical Background

Topic Understanding / Literature Review

FTDI D2XX Access

The hardware path is isolated inside ioLibrary through ioFtdiSession, ioFtdiByteStream, and ioFtdiOutputByteStream. This keeps driver concerns out of the UI layer.

MVC

ioOscilloscopeController orchestrates, ioOscilloscopeModel stores state, and ioOscilloscopeView defines the render-only boundary shared by both Qt interfaces.

Pipe-and-Filter

Scale and offset are treated as deterministic signal-processing stages through ioScaleFilter, ioOffsetFilter, and ioFilterPipeline.

Producer-Consumer

The backend keeps reading and writing decoupled through ioUsbReadController, ioDataBuffer, and ioUsbWriteController using bounded FIFO semantics.

We are treating the “literature review” portion as technical understanding: what patterns and runtime structures are required to make this kind of system reliable.

Main architectural story

  • ioQtScopeWindow hosts and switches views, but it is not a second View abstraction
  • The controller fans the same render state out to both concrete Qt views

  • Live acquisition and tee output stay in ioLiveOscilloscopeSession and ioLibrary

Code Organization

Code Structure & Responsibilities

Qt MVC

  • ioOscilloscopeController: orchestration and render fan-out
  • ioOscilloscopeModel: waveform, control, viewport, pipeline state
  • ioOscilloscopeView: one abstract View contract
  • ioQtScopeWindow: top-level host and control forwarding

Signal Pipeline

  • ioFilterPipeline: ordered processing stages
  • ioScaleFilter: multiplies samples
  • ioOffsetFilter: shifts samples vertically
  • ioRenderState: immutable view-facing payload

Live Session

  • ioLiveOscilloscopeSession: owns runtime acquisition and tee output
  • ioLiveSampleHistory: rolling waveform history
  • ioTappedReadableByteStream: mirror bytes into history
  • ioLiveFileTailByteStream: live file source

ioLibrary Pipeline

  • ioPipelineController: builds the backend pipeline
  • ioDataBuffer: bounded thread-safe circular buffer
  • ioUsbReadController: producer thread
  • ioUsbWriteController: consumer thread
Naming rule: the professor-facing implementation uses canonical io<ClassName> names, with compatibility shims treated as secondary surfaces rather than primary architecture.

Appendix B

VS Code Breakpoint / Debugging Steps

How to run it in VS Code

  1. Open the repository folder in VS Code.
  2. Open controller.py.
  3. Create a Python launch config or use Python: Current File.
  4. Set the program arguments to scope-qt.
  5. Start debugging and then interact with the Qt UI.

Breakpoints to set

  • controller.py at main()
  • io_scope_qt.py at run_scope_qt()
  • oscilloscope/io_qt_scope_window.py at _handle_source_changed() and _handle_scale_changed()
  • oscilloscope/io_oscilloscope_controller.py at start(), setScale(), setInputSource(), refreshLiveSession(), _start_live_session()
  • oscilloscope/io_oscilloscope_model.py at setScale() and _rebuild_control_pipeline()
  • oscilloscope/io_live_oscilloscope_session.py at start()
  • ioLibrary/data_buffer.py at push() and pop()

Debug flow 1: scale change in the GUI

  1. Launch scope-qt under the debugger.
  2. Change the Scale control in the window.
  3. Step from ioQtScopeWindow._handle_scale_changed() into ioOscilloscopeController.setScale().
  4. Continue into ioOscilloscopeModel.setScale() and _rebuild_control_pipeline().
  5. Use the Variables panel to show the updated scale and the reprocessed waveform state.

Debug flow 2: threaded pipeline

  1. Run python controller.py pipeline --output-mode file --output-path demo_output_recording_check.bin --input-device-index 0 --bytes-per-read 8 --bytes-per-write 8 --input-hz 20 --output-hz 20 --buffer-capacity 256 --duration-seconds 5.
  2. Break in ioPipelineController.start().
  3. Then break in ioDataBuffer.push() and pop() to show the producer-consumer handoff.
  4. Use the call stack and watch expressions to explain buffer size, thread coordination, and clean shutdown behavior.
